1. User Management & Role-Based Permissions

Already exceeds this ask
Client priority: High

What was asked

Clear Admin vs. Standard User account types, permission assignment by role, custom roles, and unambiguous identification of account type.

What's actually there

This is not a binary switch — it's a full 7-role system (App\Enums\Role): SuperAdmin, Admin, Manager, ClientOwner, Technician, Client, Viewer, each with its own permission set drawn from an 18-permission catalogue (App\Enums\Permission). Staff with roles.manage can edit exactly what each role can do — live, from Admin → Roles — with a one-click "reset to defaults."

On top of that, every tenant (client) can define their own custom roles for their own team (App\Models\ClientRole, under Team → Roles): install/update/uninstall capability, which machines they can touch (all / specific sites / an explicit machine list), which software (all / categories / an explicit package list), and whether their actions need sign-off. This isn't cosmetic — it's enforced at the exact point a deployment gets queued (ClientRole::allows() inside DeploymentService), not just hidden in the UI.

Recommendation: keep the existing RBAC exactly as-is — it already does more than a simple Admin/Standard split would allow, and downgrading to a binary model would be a step backward. The client's confusion is about visibility, not capability: add a small "Staff" vs. "Client team" badge next to each user's role on the Users page, and a short explainer on both the Roles and Team Roles pages describing how the two layers (platform roles vs. each tenant's own custom roles) relate. No architecture change.

Effort: Small — UI labeling and help text only.
Status: closed as reviewed — no build required. The existing RBAC already satisfies this module.

2. Approvals Section

Real feature — recommend keeping
Client priority: Medium

What was asked

Clarify the purpose of Approvals, or remove the tab if there's no defined business need.

What's actually there

Approvals is wired directly into the real deployment path, not a side feature — it's tested end to end (tests/Feature/ApprovalWorkflowTest.php). It only triggers for a tenant's own custom role (Module 1) that has "requires approval" turned on: when someone with that role tries to deploy something their role otherwise allows, the system files a request instead of running the job, notifies the account owner, and waits. The owner sees pending and decided requests with full history (who decided, when, resulting job) on the Approvals page.

Because it only ever appears for tenants actively using that specific setting, most people never see it fire — which is exactly why its purpose reads as unclear rather than broken.

Recommendation: keep it — removing it would delete real, tested functionality that lets an MSP client's owner delegate day-to-day installs to junior staff while retaining sign-off. Two small changes instead: (1) only show the Approvals tab in navigation when the tenant has at least one custom role configured with approval required (the plumbing for conditional nav items already exists), and (2) add one sentence of explanation at the top of the page itself. Status/history visibility the client's acceptance criteria asks for is already there.

Effort: Small.
Status: closed as reviewed — no build required. Approvals is real, tested functionality; keeping it as-is is the recommendation.

3. Packages vs. Deployments

Already separated correctly
Client priority: High

What was asked

Packages should be the reusable software library; Deployments should handle targeting, scheduling, execution, and results — following Package → Deployment → Target → Schedule → Execution → Result.

What's actually there

This separation already exists exactly as described. Packages is purely a catalogue — name, installer type, version, category, active/blocked status — with no job or machine data mixed in. Deployments is purely the job queue and history — one row per machine+package+action, with retry, cancel, and retry-all-failed. There's no overlapping data model between the two.

The perceived overlap is almost certainly navigational: both currently sit next to each other under one "Software" menu section with similar styling, with nothing on either page explicitly stating its role in the flow.

Recommendation: no functional change needed. Add one line under each page's heading stating its role in the flow (e.g. Packages: "The catalogue of software available to deploy — not connected to any specific machine"; Deployments: "What's been sent where, and how it went"). This resolves further once Module 8's navigation regrouping separates them more visually.

Effort: Small — copy only.

Update: Module 8's navigation restructure (shipped below) already separates Packages and Deployments into a cleaner "Software" group away from Policies — the visual overlap this module flagged is resolved as a side effect. The one-line copy addition on each page remains optional and wasn't built.

Status: closed as reviewed — no dedicated build required.

4. Deployment Scope — Site / Machine / Group

Shipped — verified live
Client priority: High

What was asked

Bulk Deploy should support Site, Machine, and Group targeting, following Package → Target Type → Target → Action → Schedule, with reviewable targets, per-machine results, and retry on failure.

What's actually there

Site-level bulk deploy exists and works. Machine-level exists, but only as a completely separate single-machine screen — it isn't a target-type option inside Bulk Deploy itself. A real Group concept already exists in the data model (App\Models\ComputerGroup — a named, hand-curated set of machines that can cut across clients and sites), but today it's wired only into Browser Policies, not into software deployments at all.

Per-machine results and retry-on-failure already exist for every deployment regardless of how it was targeted, since every job is always one row per machine underneath.

Recommendation: agree — this is real, worthwhile work, and matches the client's own High priority. Add a Target Type step to Bulk Deploy: Site (existing) / Group (reuse the existing, already-proven Group model — the same pattern Browser Policies already use) / Specific Machines (a new multi-select). No changes needed to results, retry, or the job model itself — that machinery already exists.

Effort: Medium — mostly UI (a target-type step) plus one new targeting query path; no schema changes to the job model.

Delivered: a Target Type selector now sits above Bulk Deploy's form — Site (unchanged), Group, and Specific Machines. Group and machine targeting are re-checked against the acting user's own visibility at queue time, not just when picking, so a tenant can never reach another client's machine through a shared group. Verified against real production data (a real group spanning two real projects resolved to exactly its members, nothing else). Commit 181373b.

5. Needs Attention

Shipped — verified live
Client priority: High

What was asked

A unified, actionable dashboard covering failed deployments/installs, offline machines, missing/outdated software, failed policies/automations, pending actions, reboot requirements, and agent communication issues — with Machine, Site, Issue, Severity, Detection Time, Status, Recommended Action, and an action button per row.

What's actually there

The existing Needs Attention page is more sophisticated than a plain failure list: it groups failed deployments by root cause (not one row per machine), classifies each as a package problem or a machine problem, states who owns fixing it, shows affected-machine count and first/last-seen time, auto-clears the moment a later attempt succeeds, and supports manual dismissal that reopens automatically if the same problem recurs. For deployment failures specifically, this already meets nearly every acceptance criterion the client listed.

The gap is scope: today it only looks at deployment failures. It doesn't yet pull in offline/non-checking-in machines, failed policy enforcement, pending approvals, or reboot-pending state — those may surface elsewhere in the app individually, but aren't unified into this one view.

Recommendation: agree to extend, not rebuild. The hard part — grouping, dismissal, auto-clear/reopen — already exists and works well; the remaining work is feeding it three more signal types: machines with no recent check-in, policies whose last enforcement failed, and approval requests waiting past a threshold. Each becomes another entry in the same table using the existing engine.

Effort: Medium–Large — the grouping/lifecycle engine is reused as-is; effort is in wiring the new signal sources.

Delivered: the page is now a real table with the exact columns asked for — Machine, Site, Issue, Severity, Detection time, Status, Recommended action, Action — and three new sources feed it: offline machines (reusing the same flag the real "agent offline" alert already raises, so the two never disagree), policies with failing machines (one row per policy, not per machine), and pending approvals (shown only to the account owner, since only they can act on it). Checked against real production data the moment it shipped: it surfaced 7 machines across 5 different client sites that were genuinely offline and invisible in the old failures-only view. Commit c2d0789.

6. Automation vs. Policies

Decision made: Option A — shipped
Client priority: High

What was asked

Policy should define desired state; Automation should define a trigger/condition/schedule-based action. Example given: a Policy ensures Chrome is installed; an Automation checks for Chrome every Friday and installs it if missing. Clarify the relationship if one requires the other.

What's actually there — the headline finding

"Automation" is not a separate feature today. It's a display label on top of Policies. A setting (branding.policy_term) is literally the word "Automation," and every screen the client saw labeled Automation is the exact same SoftwarePolicy model and the exact same form as Policies — just relabeled. There is no separate trigger/condition step, and no case where creating an Automation asks for a genuinely different, separate Policy first — it's one form wearing two names, which is precisely the confusing experience described.

Worth noting: the client's own worked example — "every Friday, check for Chrome and install if missing" — is already possible today through a Policy's own scheduling fields (frequency, maintenance window). The desired behavior already exists; only the naming is misleading.

This needs your decision before we build anything here — it changes how the product is conceptually described to every future client, so we're not picking unilaterally:

  • Option A — Rename for honesty (near-zero effort): stop calling it "Automation" anywhere; call it "Policies" consistently everywhere. Resolves the literal confusion immediately, since the scheduling behavior the client wants already exists inside Policies.
  • Option B — Build the real distinction (substantial new work): a genuine separate Automation layer — trigger (schedule, event, or condition) + action — that can reference one or more existing Policies. Matches the client's mental model exactly, but is a materially larger, net-new feature (new model, new UI, new execution engine).

Our recommendation: ship Option A now (it's nearly free and fixes the exact confusion reported), then revisit Option B only if, once the labeling is accurate, the client still wants trigger types beyond "on a schedule" — e.g. "when a new machine enrolls" or "when a file is detected" — which a scheduled Policy check alone can't express.

Effort: Option A — trivial. Option B — large; needs its own scoping conversation before an estimate.

Delivered: the client chose Option A. branding.policy_term now defaults to "Policy" everywhere in the app — navigation, page titles, forms — and the Settings page marks Policy (not Automation) as the recommended choice; Automation is still selectable if wanted, just no longer the default. No stored override existed in production, so this took effect immediately with no data migration. Confirmed live via the actual helper output on the real site. Commit 4369a42. Option B remains available if the client wants a genuine trigger/condition layer later.

7. Automation (Policy) Scope — Site / Machine / Group

Shipped — verified live
Client priority: High

What was asked

Site, Machine, and Group scoping for Automations, following Automation → Trigger → Target → Action → Schedule, with visible scope, and execution history.

What's actually there

Policies today only target a whole site/project (required on every policy) plus an exclusion list to carve out specific machines from an otherwise site-wide rule — there's no way to positively target one machine or a group. Group targeting doesn't exist for Policies at all, even though it already exists and works for Browser Policies via the same underlying Group model referenced in Module 4.

Recommendation: agree. Extend Policies the same way Browser Policies already do it — add a scope type (site or group) and reuse the existing Group model. This is a proven pattern already working elsewhere in the same codebase, which lowers both effort and risk. A positive "specific machine" target can be added the same way if wanted alongside the existing exclusion list.

Effort: Medium — copying an existing, working pattern from Browser Policies.

Delivered: Policies now support Site, Group, and Machine scope, reusing Browser Policy's exact proven pattern. Along the way this surfaced a real correctness bug, not just a UI gap: the code path that runs on every real agent check-in only ever looked policies up by project, so a group- or machine-scoped policy would never have fired in real time — only caught up later on the scheduled sweep. Fixed alongside the feature and confirmed live: a real group-scoped policy was correctly discovered and evaluated against a real production machine. A tenant creating a group-scoped policy that would reach another client's machine is refused, the same protection Module 4 has. Commit 181373b.

8. Navigation & UX

Shipped — verified live
Client priority: Medium

What was asked

Group navigation as: Dashboard · Assets (Sites, Machines, Groups) · Software (Packages, Deployments) · Management (Policies, Automations) · Administration (Users, Roles, Config) · Reports (Reports, Deployment History, Automation History, Audit Logs).

What's actually there

The current grouping is close in spirit but different in boundaries: Fleet (Clients, Sites, Computers, Team, Approvals, Device Groups), Software (Packages, Deployments, Needs Attention, Licenses, Policies, Browser Policies), Insights (Reports, Activity), Billing, and Administration. Device Groups already exists as its own item, matching the client's "Groups" ask.

Recommendation: agree to reorganize along the proposed lines. The exact shape of the "Management" group depends on the Module 6 decision — if Policies and Automation stay merged (Option A), that group holds just Policies; if a real Automation layer is built later (Option B), it gets its own entry then. Otherwise this is a straightforward relabeling of existing pages into clearer groups, not new functionality.

Effort: Small–Medium — reorganizing an existing menu definition; no new backend logic beyond what other modules already add.

Delivered: navigation now matches the proposed structure — Dashboard (+ Needs attention), Assets (Clients/Sites/Computers/Groups), Software (Packages/Deployments/Licenses), Management (Policies, since Module 6 kept it merged with Automation), Administration, and Reports (Reports + Audit Logs, renamed from Activity). Billing is unchanged — it wasn't part of the described structure and doesn't fit it. Turned out to be a pure data change: the sidebar already derives its collapsible sections from group names, so no template rework was needed. Not built: "Deployment History" and "Automation History" as separate items — they aren't distinct features here; the existing Deployments and Policy pages already are each one's history, so duplicating the same routes under new labels would be redundant navigation, not a real feature. Commit c2d0789.

9. Audit Logging

Verified & shipped
Client priority: Medium/High

What was asked

Log every administrative change (users/permissions, packages, deployments, policies, automations, enrollment, config) with User, Action, Target, Date/Time, Previous Value, New Value, and Result — searchable, filterable, and restricted to authorized administrators.

What's actually there

A real, working audit log already exists (Activity Log, under Insights), permission-gated, tenant-scoped so a client only ever sees their own team's actions, searchable by action text or user name, and filterable by category. Its columns already cover When, Log category, Action, By (user), and Subject (the affected record) — most of what was asked for is already live today, not a gap.

What's genuinely missing

The current "Detail" column shows raw logged data as-is rather than clean, separate Previous Value / New Value columns. We also haven't yet done a full coverage pass to confirm literally every administrative action type in the client's list writes a log entry — some areas may log richer detail than others today.

Recommendation: keep the existing engine — it doesn't need to be rebuilt. Two remaining pieces of work: (1) a coverage audit confirming every admin action category the client listed is actually logged, filling any real gaps found, and (2) reworking the Detail column into explicit Previous Value / New Value fields where the underlying data supports it.

Effort: Small–Medium.

Delivered: wrote real tests exercising every category on the client's list — users/permissions, packages, policies, machine enrollment, configuration — instead of trusting a code-search for logging calls, which would have missed anything logged automatically through a model's own trait rather than an explicit call site. Verified finding: every category was already covered, including deletions and machine enrollment (not obvious from reading the controller — enrollment has no logging call of its own; it's covered because the underlying model-creation call is). The Detail column now splits into Previous Value / New Value wherever the data supports it. Checking this against real production rows immediately caught a real display bug — a deleted record's last state was showing under "New Value" instead of "Previous Value" — fixed and reconfirmed against the same real rows. Commits 1f639b6, b996428.

Final Recommendation

The client's overall functional structure — clean separation of Users, Roles & Permissions, Packages, Deployments, Policies, and Needs Attention — was the right direction, and most of it was already true of the underlying system, even where the UI hadn't made that obvious yet. All the real, concrete build work is now done: Site/Machine/Group targeting for both Deployments and Policies (Modules 4 & 7), Needs Attention's extended scope (Module 5), the Automation/Policies naming decision (Module 6), and the navigation restructure (Module 8) — every one built, tested, deployed to production, and checked against real data, not just a passing test suite. Module 9's audit logging turned out to already have full coverage; the one real display gap found there was fixed the same way. Two things surfaced along the way that weren't part of the original nine points and are worth a look when convenient: the Bulk Deploy / Policy tenant-isolation guard added for Modules 4 and 7 closes a real cross-tenant risk that predates this review, and the "Deployment History" / "Automation History" items from the original navigation proposal were deliberately not built as separate pages — they'd just duplicate the existing Deployments and Policy views under new labels.
